# 技术背景：为什么 P5 需要这套方案

## 摄像头在做什么

P5 的十几个摄像头在行驶中持续采集画面，但数据直接进入辅助驾驶芯片（Xavier XPU）做感知计算，**不写入存储器**。360 影像是把处理后的画面显示到屏幕上供人看，同样不落盘。

社区里流传一种说法：手动进 360 界面点录像，能录一小段（上限 5 分钟），存进车机相册。这确实是原生能力，但它有三个硬伤：

1. 录完自动停，不循环
2. 相册不会自动覆盖旧文件，写满会影响车机速度
3. 行驶中碰撞/急刹不会自动触发锁定保存

## 为什么特斯拉能做到

特斯拉的行车记录仪复用 Autopilot 摄像头，靠的是全栈自研芯片：ISP 集成在自研 FSD 芯片里，架构设计之初就预留了把摄像头画面分一路做录像的通路，一个 OTA 就能开启。

P5 用的是英伟达 Xavier，其硬件 ISP 专门服务辅助驾驶。据小鹏工程师在公开社区的说明，再分一路做录像会增加内部数据流延迟、影响辅助驾驶稳定性，因此该功能前期规划过、中期因优先级放弃。这是架构取舍，不是"软件没做"。

## ADB 改变了什么

ADB 本身**不能**让第三方 APP 拿到摄像头原始数据——视频流仍锁在 XPU 里。但 ADB 能让车机执行 shell 命令，于是出现两条新路：

- `screenrecord` 是 Android 系统自带工具，能把**屏幕上显示的内容**录成 MP4。既然 360 影像能显示到屏幕上，就能录下来；文件由脚本自己管理，想覆盖就覆盖。代价是录的是"屏幕画面"而非摄像头原始流，含 UI、竖屏。
- `input tap` 能模拟点击原生录像按钮，配合定时器反复点；画质是原生的，但要处理界面自动退出和相册路径问题。

## 为什么 GitHub 上的小鹏项目帮不上 P5

社区里有几个相关开源项目：

- `psuurbach/xpeng-dashcam`：录像网页播放器
- `stevelea/XpengUSB` / `FA9US/XpengUSB`：树莓派伪装 U 盘，把录像自动归档到 NAS

它们处理的是 `XP_DCIM/DVR_xxx_front.mp4` 这类文件——**新款小鹏（G6/G9/X9/P7+，天玑 XOS 5.x）车机自带 DVR，插 U 盘就循环录像**。P5 不写这类文件，所以这些工具在 P5 上没有用武之地。

## 已知未解问题

- 碰撞事件自动锁定片段：车机 shell 拿不到 G-sensor 事件，暂无软件解法
- 竖屏画面与 UI 遮挡：录屏方案的固有缺陷
- 车机重启 / OTA 后后台进程失效：需要外部自动化工具触发
- 不同 Xmart OS 版本 360 界面行为差异：需要真车众测补充
